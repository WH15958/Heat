# Heat Git Workflow

Use this skill when the user says `/git`, asks to commit Heat repo changes, asks whether docs/tests are needed before commit, or asks to push after a commit.

## Core Rule

`/git` means:

```text
inspect changes -> validate as needed -> update docs as needed -> stage relevant files -> commit -> wait for user confirmation before push
```

It does not mean auto-push, reset unrelated files, clean untracked files, or run every build for documentation-only changes.

## Fast Inspection

Use narrow commands first because this Windows workspace can stall on broad PowerShell output.

Prefer:

```powershell
git status --short -- <paths>
git diff -- <paths>
git diff --cached --check
rg --files
rg -n "<pattern>" <path>
```

For large output, use Node `spawnSync` or targeted file reads instead of wide PowerShell pipelines. Avoid unscoped recursive `Get-ChildItem`, large `Format-Table`, and huge diffs through PowerShell.

Always identify and leave unrelated user changes unstaged.

## Validation Decision Matrix

Choose the narrowest validation that proves the changed behavior.

| Change type | Checks |
| --- | --- |
| Docs, agent rules, or skills only | `git diff --check -- <paths>` and targeted content review |
| Python backend | `python tests\test_metadata.py` plus relevant import checks |
| Campaign / planner | Backend checks plus `python -c "import src.web.api.campaigns; import src.campaigns.store; import src.ml.planner"` |
| Frontend source | `cd frontend; npm run build -- --mode production` |
| YAML parser or experiment engine | Metadata tests plus targeted import or behavior checks |
| Hardware-facing behavior | Software checks plus tell the user real-device/lab smoke testing is still required |

Common backend import check:

```powershell
python -c "import src.web.app; import src.web.api.experiments; import src.web.api.ws"
```

If `pytest` is installed, use targeted pytest files. If it is not installed, say so and use an equivalent targeted Python validation when practical.

## Documentation Decision Matrix

Update only the docs that match the change.

| Change type | Documents |
| --- | --- |
| New page, button, user operation, or visible behavior | `docs/user_guide.md` |
| API path, request/response shape, backend architecture, or developer workflow | `docs/developer_guide.md` |
| YAML action, wait type, metadata field, or experiment file format | `docs/experiment_yaml_spec.md` |
| `sample_id`, `samples.csv`, campaign, trial, recommendation, or characterization flow | `docs/campaign_workflow.md`; also `docs/user_guide.md` if user-facing |
| Validation, branch, commit, merge, push, or `/git` workflow | `docs/testing_and_merge_flow.md` |
| Project positioning, major capability list, setup, or top-level usage | `README.md` |
| Long-lived AI/project facts, hardware boundaries, or agent rules | `context/PROJECT_CONTEXT.md` and/or `AGENTS.md` |
| Internal implementation only, no interface or behavior change | Usually no user docs; update `docs/developer_guide.md` only if architecture changed |

For long Chinese docs that show mojibake in terminal, avoid wholesale rewrites. Prefer focused edits or a new focused doc.

## Generated Files

`frontend/auto-imports.d.ts` and `frontend/components.d.ts` are generated by frontend plugins. After builds, check content diff and EOL state before staging them. Commit them only when declarations changed meaningfully.

## Commit and Push

Before commit:

1. Stage only relevant files.
2. Run `git diff --cached --check`.
3. Commit with a concise prefix such as `feat:`, `fix:`, `docs:`, `refactor:`, or `test:`.
4. Summarize validation and any skipped checks.

After commit:

- Do not push unless the user explicitly confirms.
- If the user confirms push, check remotes and push the current branch to `origin` and `github` when both are configured:

```powershell
git push origin <branch>
git push github <branch>
```

## Git Loose Objects

If Git reports many unreachable loose objects, explain that Git has accumulated temporary or unreachable objects from commits, amends, rebases, aborted operations, or object writes. It is usually not a code problem.

Do not run cleanup as part of `/git` by default. Offer a separate maintenance step:

```powershell
git count-objects -v
git gc
```

Use `git gc --prune=now` only after the user accepts more aggressive cleanup.
