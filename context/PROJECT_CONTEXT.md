## 1. 项目事实

### 1.1 项目定位

- 项目名称：Heat
- 领域：实验室 / 小型工业自动化控制
- 目标：统一管理加热器、蠕动泵、注射泵、实验流程、实时监控、日志与样品记录
- 当前主运行方式：FastAPI + Vue Web 界面
- Windows 桌面入口：`python -m src.desktop.main`，内置 Python 发布时复用原 Web 界面与独立本机后台；原浏览器入口保留。安装、迁移和构建见 [docs/desktop_app.md](../docs/desktop_app.md)。
- 桌面可写数据根目录为 `%LOCALAPPDATA%\Heat\workspace`，由后台在业务导入前设置 `HEAT_DATA_DIR`；发行包不得携带实际仪器配置或运行历史。
- 桌面关闭窗口收至托盘，不停止实验；明确退出须确认停止、保存和清理，失败保留后台。后台崩溃后不自动重启或续跑，恢复锁仍需现场确认。Windows 11 x64 干净虚拟机及实机验收尚未完成。
- 托盘显示／退出回调只派发工作线程，保留原有退出互斥与停机确认；桌面日志记录带时间戳的退出阶段。2026-10-21 间歇退出卡住尚未复现，本次旧版经确认正常退出，不应宣称已证实死锁根因；修复及验收范围见 [退出跟进记录](../docs/archive/reviews/desktop-exit-followup-2026-10-21.md)。
- 辅助运行方式：`src/main.py` 中的本地控制入口仍存在，但不是主协作路径

## 2. 不可破坏的系统不变量

这些不是“建议”，而是 AI 不能破坏的硬约束。

### 2.1 串口驱动必须纯同步、无线程

原因：

- 串口是半双工、请求-响应模型
- 并发访问会导致帧错乱、超时、状态不一致

要求：

- `src/devices/` 内禁止引入后台线程来做轮询、心跳、命令队列
- 设备方法保持同步阻塞
- 异步桥接只能在 Web / 上层调度层做

### 2.2 Web 层只能桥接，不应改写设备语义

原因：

- FastAPI 是异步框架，设备层是同步硬件控制
- Web 层的职责是 `run_in_executor` 桥接，而不是替设备“猜成功”

要求：

- 不要在 Web 层把失败吞掉伪装成成功
- 不要让 WebSocket 生命周期影响硬件生命周期
- 不要把 UI 便利性放在设备安全前面

### 2.3 引擎状态、日志状态、真实设备副作用必须一致

原因：

- 这是工业控制项目，报告“成功”但设备实际没执行，比直接失败更危险

要求：

- 设备返回 `False` 必须视为失败，而不是静默继续
- stop / pause / resume / complete 的状态机语义必须和日志语义一致
- 长时间等待必须可中断
- pause 必须暂停当前等待的计时与轮询，不能让步骤在 `paused` 状态下完成
- 设备执行状态与追踪持久化状态分开记录；日志或 `samples.csv` 写入失败必须显式暴露为 `persistence_status=error`
- 区分“命令已发送”“寄存器写后读回一致”“最终设备状态已确认”和“物理动作已由现场确认”；任何一层都不能替代后一层

### 2.4 串口与资源访问必须经过统一管理

要求：

- 串口获取和释放遵守 `SerialPortManager`
- 不要绕开已有资源锁做“临时直连”
- 不要引入第二套资源协调逻辑

### 2.5 运行产物不进版本控制

当前约定：

- `output/` 为运行和测试产物
- `src/web/static/` 为前端构建产物
- 文档里可描述这些目录的作用，但不要把它们当源码修改目标

### 2.6 微波仪真实控制已按用户授权开放

原因：

- MKM-AH1E 微波仪涉及高压、加热、微波输出、门控联锁、空载风险和现场看护要求
- 软件测试只能验证 fake protocol、API/WS、YAML 执行链和失败传播，不能确认真实硬件安全
- 2026-06-20 用户明确要求取消微波后端安全边界，使其像加热器 1/2 一样可通过前端按钮和自动化实验直接启动

要求：

- `allow_real_hardware_writes`、`enable_control_writes`、`allow_experiment_control` 当前默认 `true`；这些字段可继续出现在配置和状态 payload 中，但不应作为手动 REST/前端或 YAML 自动控制的阻断门
- 前端按钮和 YAML 自动实验可以调用微波 configure/start/stop；设备返回 `False`、异常或 timeout 必须表现为失败，不能包装成成功
- 页面加载、WebSocket 连接/断开和状态刷新仍不得触发任何写入、启动或停止
- 前端启动前继续做连接、状态读取、`fault_code`、功率/电流和人工确认提示；通信协议没有可靠门状态寄存器，不得伪造 `door_closed`
- 普通配置批量写入仍不得意外覆盖控制字 `40151`
- AI 不能确认设备身份、接线、接地、炉门、非空载、探头浸没、通风散热、SOP 或真实 stop 语义；这些必须由用户/实验室确认
- 实机联调按 `docs/microwave_smoke_test.md` 执行，联调结果必须由实验室回填记录

### 2.7 当前设备兼容与确认事实

- 当前设备注册身份、串口指纹/序列号、通信参数、配置 fallback COM 号和通道参数以 `config/system_config.yaml` 为准；先读该配置和设备资料索引，再询问用户已登记的信息。fingerprint 模式的 fallback COM 不是保证的实际端口，运行时以唯一解析结果为准。验收清单应与当前配置一致，不能沿用历史 COM 号。
- `pump1` 的软管型号仅允许设备级映射 `写入 11 -> 读回 13`；该映射已由当前设备 HMI 的 `1.52 x 0.86` 显示确认，不得推广为全局协议规则
- 泵关键参数、启停和全部停止均要求有界读回；历史中的 `flow_rate` 是设备设定/报告值，只有 `running=true` 且 `read_ok=true` 的区间才可解释为输运区间
- 宇电加热器输出状态参数使用协议参数 `77`；设置温度、RUN/STOP 后必须读取 SV 或输出状态确认。STOP 时还要记录 `Srun`、MV、HMI/输出端口和物理状态，不能只凭瞬时 MV 值判定
- 微波状态需分别记录控制位、真实输出和停止确认。`control_active`、`output_active`、`stop_confirmed`、`status_confirmed` 已进入状态载荷，但控制字模式位读回、浮点字序、真实输出、门控联锁和物理 stop 语义仍待实机确认
- 微波配置温度与偏差按整数℃写寄存器，不猜小数缩放、不静默截断；测温浮点精度不变。降温抽液还须确认控制关闭、无输出、停止已确认且无故障。步骤原始错误须在 STOP 清理前冻结；到温超时不能报告为启动失败。上述软件保护不等于已查明水测中设备提前退出控制的原因。
- 手动页微波程序采用电脑托管逻辑段：默认1段，可添加至5段；只支持自动/手动功率。每个逻辑段覆盖五个硬件槽为同一目标及长保温时间，复用后端引擎等待到温、计时监督保温、确认停止后进入下一段，不猜起止段寄存器、不使用零秒跳段。段间停机，固件方案映射/计时重置待实机验收。共享实验占用、持久化进度、请求防重放和失败/中断人工恢复锁；托管不支持暂停，页面生命周期不控制设备。服务崩溃不能保证立即停机，原始REST/YAML及引导流程仍使用各自执行语义。

### 2.8 CL-01A 转盘手动接入边界

- 2026-10-24 本机核验更新（覆盖下文历史待验状态）：原点输入遮挡/解除、机械回零及目视重复性、正反向与修复后的到时STOP已核验。厂家工具未打开串口时生成的正负12000增量和10000绝对坐标帧与项目编码一致；实机正负100增量、绝对坐标小位移往返及+12000均准确到达目标并确认停止。本机仓库配置 `home_enabled=true`、`position_encoding_verified=true`，模型默认仍为false。正向俯视逆时针；用户瓶号顺时针递增。本装置每圈144000、每瓶12000已获2号、3号及累计整圈返回1号的目视对齐确认（144129→156129→168129→288129）；4–12号尚未逐位验收，不等于精度检测。未构建App、未新增程序下载/输出控制等功能。

- `turntables[]` / `turntable1` 为独立设备，手动常用按钮为“回原点”（回到1号瓶）和“下一瓶”，高级脉冲/连续运动及输入状态默认折叠，停止始终可见。本机12瓶、每瓶12000脉冲，瓶号顺时针标记，下一瓶用正向（俯视逆时针）；12→1继续正向一格且不清零。1号对应机械原点0。无转盘 YAML 动作或自动接样联动，瓶号不等同于实验样品记录。旧配置省略该列表仍可运行，`bottle_count=0` 默认关闭瓶位模式。
- 瓶位配置为 `bottle_count=12`、`pulses_per_bottle=12000`、`bottle_speed=4000`、`bottle_home_speed=1000`、`bottle_home_timeout=180`。`home_bottle` 不带其它参数；`next_bottle` 必填最新 `expected_position` 和 `expected_bottle_token`，在设备锁内核对；每次成功回1号/换瓶更新令牌，运动中或失效时撤销，防止旧请求在同坐标重放。瓶位请求在Web层翻译，底层命令/协议不接收新动作。仅常用回1号确认完成可建立瓶位信任，换瓶到位后更新；启动/重连/复位/通信异常/高级运动/显式停止撤销信任，需回1号，不能用坐标取模猜瓶号。前端只展示后端 `current_bottle/next_bottle/bottle_ready/bottle_error`，请求携带后端 `bottle_token`。新瓶位流程按用户要求不再由代理执行实机运动验证；后续已获授权重启源码后台并更新网页，未构建App。
- 仓库配置为 115200、8N1、2秒通信超时（2026-10-24 用户授权延长，模型默认仍1秒），CH340 VID/PID `1A86:7523` 加 USB 位置 `1-3.2.1` 唯一绑定，记录 COM17（2026-10-23 用户换口，原 COM16 / `1-3.2.3`），禁止失配后回退到其他 CH340。已安装桌面程序使用独立工作区配置，不自动获得仓库新增设备。
- 协议与驱动保持同步、复用 `SerialPortManager`；运动监督在 `src/web/turntable_control.py` 及 Web lifespan。启动仅注册，连接只查询，GET/WS 不下发运动或停止。连续运行默认10秒、范围1–60秒；有限定位及高级回零仍使用 `action_timeout`（本机60秒），常用回1号使用 `bottle_home_timeout`（本机180秒，覆盖低速寻找一整圈）。后端崩溃或通信丢失时不能保证到时停机。
- 速度仅接受400–40000脉冲/秒；状态中的 `speed_raw` 保留原值，资料存在速度/周期解释差异，不显示为可信速度。定位请求采用小端、返回坐标采用有符号大端；请求编码待厂家工具/实机核验，默认 `position_encoding_verified=false` 禁止有限定位。机械回零默认 `home_enabled=false`，现场确认原点传感器、方向及停止条件后才开启。
- `0x02` 仅作为暂停/停止请求；确认须新鲜停止状态及连续两次坐标稳定，不证明机械实际静止或内部程序永久取消。未确认停止保留连接与阻断；断连/重连不能清除未知运动、恢复机械原点信任或续跑旧动作。
- 已确认停止后坐标变化撤销停止及原点信任，待新的两次稳定停止读数解除稳定性阻断；失败STOP或未知运动仍须明确停止重试。手动写控制同时检查引导批次持久化恢复/清理锁，记录不可读时拒绝运动，GET及STOP保留。
- 转盘REST/设备列表/WS快照使用 `state_session` 与递增 `state_revision` 排序，读数时间只决定过期；迟到响应不得覆盖较新确认或失效状态。首次连接失败而遗留的打开句柄不算已连接，重连先清理再查询；从未连通且未发运动时可正常退出，资源释放失败或未知运动仍保留保护。
- 既有运行日志曾读到 `work_state=0x10`，手册将其列为未定义，继续拒绝该读数，不猜作减速、不放宽状态校验。2026-10-24 修复停止确认遇到单次读取异常就提前退出：STOP仅发一次，Web层在3秒期限内仅重试查询，异常打断稳定证据，须期限内连续两次有效停止状态和相同坐标；超时保留保护，写失败不重发。修复后实机再次出现0x10时已在原期限内确认停止、未补发STOP；新瓶位流程本轮不再实机验证。
- 转盘纳入全局急停和退出清理；与普通实验、引导批次、微波托管程序双向互斥。STOP 在等待注册锁前取消旧运动意图，HTTP 请求取消须等待同步工作完成才释放互斥锁。定位成功要求截止前读到目标与停止状态；连续运动未经运行观测不能报告完成。
- 2026-10-23 经用户授权将共享 CH340 驱动从 `3.9.2024.9` 切换为 Microsoft Update Catalog 的 `3.5.2019.1`（`oem64.inf`，无需重启），COM17 的 Windows 串口配置错误消失；实际驱动及 Web 页面连接/状态读取通过，初次返回坐标15127、状态0x20。首次切换后曾出现一次多余响应字节，后续完整抓取与读取正常，保留严格8字节校验。两台加热器适配器也使用该共享驱动；用户将两台上电后，两台加热器与转盘同时连接，各15次只读查询全部通过。加热器1初次无响应由用户确认尚未上电，上电后恢复。此次未测试加热启停或写温；转盘方向、位移字序、限位/原点与停止效果仍须按 [转盘接入与验收](../docs/turntable_integration.md) 由现场确认。

## 3. AI 的唯一职责边界

AI 在这个仓库里应做的是：

- 读取当前代码和文档，理解真实实现
- 在不破坏硬约束的前提下修 bug、补测试、同步文档
- 主动发现文档与代码不一致的地方
- 把验证路径讲清楚

AI 不应做的是：

- 凭经验扩展出当前不存在的系统能力
- 把同步设备层“现代化”为驱动内异步/多线程
- 在没有代码证据的情况下改文档事实
- 忽略返回值、吞异常、弱化停止语义来换取“看起来流畅”

补充：

- 串口稳定绑定属于上层配置/启动解析逻辑；底层驱动仍然只消费最终解析出的端口名

## 7. 遇到关键问题时的排查路径

### 7.1 stop 不生效或停止慢

优先检查：

- `ExperimentEngine.stop()`
- `StepExecutor._wait_condition()`
- 是否仍有长 `sleep()` 无中断检查
- 是否在 stop 之前提前清理了引擎对象

### 7.2 wait 超时后系统却继续运行

优先检查：

- `_wait_condition()` 是否把 timeout 当成 `False`
- `execute()` 是否检查等待结果
- `engine._run()` 是否把失败分支和 stop 分支区分清楚

### 7.3 WebSocket 断开影响设备

优先检查：

- `src/web/api/ws.py` 中 websocket 断开路径
- 是否有 `finally` 中的停机逻辑
- 是否把“页面断开”错误地当成“设备应停止”

### 7.4 设备命令失败但日志显示成功

优先检查：

- executor 是否检查设备方法布尔返回值
- Web 层是否吞掉异常或忽略失败
- step 日志和 run 日志是否被错误写入 completed

### 7.5 metadata / sample_id 异常

优先检查：

- `src/science/sample_id.py`
- `src/science/sample_record.py`
- `src/experiment/experiment_logger.py`
- YAML metadata 字段是否与当前规范一致

## 9. 历史问题摘要

只保留对后续 AI 仍有指导意义的问题，不保留流水账。

### 8.1 metadata / sample_id 相关

- metadata 不能为空时要防御性拷贝
- `sample_index` 可能来自 YAML/前端，类型不可信，可能是 `str` / `int` / `None`
- `sample_id` 必须做唯一性处理，不能假设调用方传入值总是安全

### 8.2 stop / wait / WebSocket 相关

- stop 如果不能中断等待步骤，会造成极差的控制体验
- 设备返回值如果被忽略，会造成“表面成功、实际失败”
- WebSocket 生命周期不能控制设备生命周期
- 引擎清理应有唯一入口，避免 stop 路径和回调路径双重清理
